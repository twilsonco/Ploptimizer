`job-config.json` is the shop tier of the generate pipeline: its
values are injected as the top-most (job/plate) layer of the cascade,
so every label may still override them, and a field set to `null` (or
omitted) means "no configured default" — the code fallback applies.
Precedence: job YAML > `job-config.json` > code fallback. All units
are **inches**. Every key is validated at load against
[`job_config.schema.json`](job_config.schema.json) (this file's source
of truth): unknown keys and out-of-range values fail the run with
every problem listed at once.

Add `"$schema": "./docs/skills/engraving-jobs/engraving-job-complete-reference/references/job_config.schema.json"`
to a config file to get per-field hover documentation in a JSON-aware
editor (the path is relative to the config file; for a config kept
outside the repo, copy the schema beside it or use a `file:` URI).

Sections below the `Field audit` heading are rendered from the live
`job-config.json` (key presence and tool options) and are excluded from
the docs byte-pin; everything above is derived purely from the model.

### `HoleLocation`

Enumeration of valid hole locations on a label.

Besides the eight atomic positions (four edges and four corners), two
group shorthands are accepted for the most common drilling patterns:
`corners` (all four corner holes) and `sides` (the left and right
edge holes). Groups are expanded into their atomic members at schema
validation time (see :data:`HOLE_LOCATION_GROUPS`), so downstream
consumers only ever see the eight atomic locations.

| Value | Description |
|---|---|
| `left` | Hole on the left edge. |
| `right` | Hole on the right edge. |
| `top` | Hole on the top edge. |
| `bottom` | Hole on the bottom edge. |
| `top-left` | Hole at the top-left corner. |
| `top-right` | Hole at the top-right corner. |
| `bottom-left` | Hole at the bottom-left corner. |
| `bottom-right` | Hole at the bottom-right corner. |
| `corners` | Group shorthand for all four corner holes. |
| `sides` | Group shorthand for the left and right edge holes. |

### `TextHAlignment`

Enumeration of valid horizontal text alignment modes for a text line.

The alignment anchors the rendered line within the label's inner content
area (label width minus both margins). `left` places the line's
left-most point precisely at the left margin; `right` places the
line's right-most point precisely at the right margin; `center`
(the default) centers the line horizontally.

| Value | Description |
|---|---|
| `left` | Align text to the left margin. |
| `center` | Center text horizontally. |
| `right` | Align text to the right margin. |

### `LayoutMode`

Enumeration of plate fill-order preferences for bin packing.

`rectpack` has no sort option that controls fill order directly (the
emergent order is a side effect of placement tie-breaking), so
`columns` is realized by packing in a transposed frame with a
bottom-row fill algorithm and mapping every placement back into plate
space (see `plt_optimizer.generate.packing.layout`).

The `*-simple` modes bypass `rectpack` entirely: labels are placed
one at a time in strict content order on a flush grid, never rotated
(this mirrors the VisionPro "Multiples" / EngraveLab "Badges"
behavior). `columns-simple` fills each column top-to-bottom before
extending rightward; `rows-simple` fills each row left-to-right
before extending downward. A column (resp. row) spans the widest
(resp. tallest) label placed in it, fixed for its whole length, so a
1x3/1x4 mix starts the second column at x=4 for the entire column.
Round labels are exempt: they always keep the ellipse-packer layout
optimization regardless of mode.

| Value | Description |
|---|---|
| `rows` | Fill the plate row by row (rectpack). |
| `columns` | Fill the plate column by column (rectpack). |
| `rows-simple` | Grid-fill each row left-to-right, then down. |
| `columns-simple` | Grid-fill each column top-to-bottom, then right. |

### `CounterStyle`

Enumeration of enumerated-list counter styles.

The style decides how an :class:`EnumerateBlock` renders the number of
each of its items (see :func:`plt_optimizer.generate.list_counter.format_counter`).
`decimal` is the historical/plain numbering; the alpha styles count in
letters (bijective base 26, so `z` is followed by `aa`); the roman
styles count in Roman numerals.

| Value | Description |
|---|---|
| `decimal` | Arabic numerals: 1, 2, 3, ... |
| `lower-alpha` | Lowercase letters: a, b, c, ..., z, aa, ab, ... |
| `upper-alpha` | Uppercase letters: A, B, C, ..., Z, AA, AB, ... |
| `lower-roman` | Lowercase Roman numerals: i, ii, iii, iv, ... |
| `upper-roman` | Uppercase Roman numerals: I, II, III, IV, ... |

### `LabelShape`

Enumeration of valid label boundary shapes.

`rect` (the default) is the historical behavior: the label boundary is
the `width` x `height` rectangle, the packer packs that rectangle, and
every collision check measures the rectangle. `round` makes the boundary
an ellipse with semi-axes `width / 2` and `height / 2` -- a circle when
the two are equal -- which switches the label onto the adjacent
ellipse-packing pipeline (see :mod:`plt_optimizer.generate.packing.ellipse_packer`)
and makes the collision checks measure the ellipse boundary.

| Value | Description |
|---|---|
| `rect` | Rectangular label boundary. |
| `round` | Elliptical (round) label boundary. |

## Required-when-unconfigured (job-config gate)

When a `--job-config` path is in play, these fields must be supplied by
the config **or** the job spec (job level, or on every label); missing
everywhere aborts parsing with `JobConfigError`:

- `hole_margin`
- `hole_text_collision_distance`
- `max_h_compress`
- `min_hole_margin`
- `plate_width` / `plate_height` (enforced separately: needed whenever
  plates are undeclared, i.e. unbounded auto-allocation)

Without a config path (direct API / test callers), every field keeps its
code fallback and nothing is required.
