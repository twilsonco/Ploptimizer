I've got a python tool for generating HPGL (PLT Files) toolpaths. I render fonts using ttf font files, but I'm adding the ability to "reverse engineer" engraving fonts from programs like EngraveLab/VisionPro. The process is simple:
1. Create a file with all the printable ASCII characters, in order, left-to-right top-to-bottom in several rows. (Multiple rows are necessary because of the driver-dependent maximum sheet size that can be too small to fit all printable ascii characters on a single row. You can use a very small text height in order to decrease the horizontal space required, but at very small character heights, you begin to coarsen the characters in the generated toolpath. So, in order to use sufficiently sized characters, multiple rows are necessary.)
2. Use a python script to chunk the HPGL commands for each character based on the empty space between characters (commands translated to be origin-centered and then scaled to an equivalent 1 inch font height)
3. Store each character's HPGL commands in a json dictionary of dictionaries (font name -> character -> string of HPGL commands).
4. Now you can scale and translate each character's HPGL commands in order to build/render text using any of the fonts for which this process has been completed.

I have a separate script that creates a showcase PDF showing each font that was extracted in this way, and looking at the results, I realize that it was a mistake moving each character to its own relative origin for storage because that destroys information about where each character sits vertically relative to the baseline. When creating text using these stored characters, they all sit vertically centered at the text midline rather than the baseline. For example, a period "." becomes a vertically centered dot on the line.

I need to think of how to modify this process so that when I eventually place scaled copies of the character commands to generate text, I can vertically translate each properly-scaled character so that it ends up with the correct vertical placement relative to the baseline. The goal being to achieve the same baseline-relative vertical placement as the equivalent text created with the EngraveLab/VisionPro software.

Regarding the changes to steps 1 and 2 (the design/creation of the document in EngraveLab/VisionPro and the extraction script), some characters can be assumed to perfectly occupy vertical space on their line from the baseline to the cap line (e.g. capital flat-topped and flat-bottomed letters "E", "Z", etc.). We could use those characters as reference points for determining the baseline and cap line positions when extracting and storing the HPGL commands for other characters. We would thus change the set of characters used in the EngraveLab/VisionPro document so that each row of characters begins and ends with the same reference character, ensuring consistent vertical alignment cues across each row. This has the secondary benefit of validating extracted characters because each extracted row can be checked for the expected reference character. e.g. if "E" is the reference character, then we expect to find it at the beginning and end of each row as well as at its designated position in the ordered list of ASCII characters. Every other extracted character's vertical placement can be determined relative to the reference character's baseline and cap line positions.

For storing additional information with the extracted characters, I'm unsure what information should be stored. One possibility is to store the baseline and cap line positions for each character, relative to the character's origin. This would allow the rendering process to correctly position each character vertically, even after scaling. Another possibility is to store the vertical extents (top and bottom) of each character, which could also be used to determine the correct vertical placement relative to the baseline.

While considering this, it's important to note that, even if characters are not stored origin-centered, all x+y (aspect ratio conserving) scaling should be done relative to the character origin. For example, if working with a comma "," character, scaling it relative to the midline will have the effect of also translating the comma up or down. So whatever process we use needs to allow us to a) scale a character to a desired size, and b) still be able to correctly position it relative to the correct baseline, regardless of what amount of scaling was applied.
