# TODO List

- [ ] Add support for bullet lists and enumerated lists. This hopefully can utilize some of the existing code for the `new_line` field.
  - This will take some thought for how to implement.
  - The bullet/enumerated list fields could be alternatives to `text` within a `content` block, allowing each `text` item to either be a simple text line or a bullet/enumerated list item, called `itemize`/`enumerate` respectively.
  - For bullet lists, we could include a `bullet_string` field to specify the character(s) used for each bullet (e.g., "•").
    - `bullet_string` should be specifiable for each `text` item in the bullet list as well.
  - For enumerated lists, we could include a few helper fields:
    - `start_index`: The starting number for the enumerated list (default 1).
    - `counter_style`: The style of the enumerated counter ("decimal", "lower-alpha", "upper-alpha", "lower-roman", "upper-roman").
    - `counter_prefix`: A string to prefix each enumerated item with (e.g., "Step " for "Step 1", "Step 2", etc.).
    - `counter_suffix`: A string to suffix each enumerated item with (e.g., "." for "1.", "2.", or ")" for "1)", "2)", etc.).
  - In addition to handling the placement of bullets and counters, these will work well with `optimize_line_content` (and `optimize_line_content_max_lines`), and when a bullet/enumerated item spans multiple lines, its 2nd and subsequent lines will be properly left-aligned with the start of the text, not the bullet or counter, similar to how it works in MS Word, LaTeX, etc.
- [ ] Implement `extra="forbid"` in the Pydantic models to prevent unexpected fields from being accepted. This will help catch typos and enforce strict schema adherence, ensuring that only the defined fields are allowed in the input data. This should be done everywhere on the basis that if a field is added, the user expects it to work, and if the field has a typo, the user needs to know about it.
- [ ] Improve "all" pdf preview by supporting text/background colors. We already have the optional `material` and `text_color` fields in the job spec yaml files. The `text_color` field has an associated `TextColor` class that includes support for abbreviated 1-char codes. And typically, the difference between materials is the text/background colors. Taken together, I think the colors used in the "all" preview could be derived from the `material` field alone, or from both fields to provide a more accurate representation of the final output. 
  - For example, even if no `text_color` is specified, if the `material` is `bw`, then we assume a convention where the first character is the background color and the second character is the text color (i.e. the first character is the top layer and the second character is the core); that's sufficient to get background and text colors for the preview. 
  - We could also support an alternative convention where the material uses full color names with one of a few possible delimiters (e.g., "red-on-white", "red:white", "red|white", "red/white") to specify the background and text colors explicitly. 
  - There's also three-color possibilities, e.g. `wrb` for white-red-black, where the first character is the top layer (background), and the next two characters represent the middle and bottom layers respectively; in this case, we only know the background color for sure, and the user will need to specify `text_color` as necessary to accurately represent the text color in the preview.
  - So the background color can be determined from `material`, and `text_color` can override the text color for the preview.
  - Additionally, assuming the first part of the `material` string specifies the color, anything after that can be ignored for the purpose of determining the background color in the preview. e.g. the `material` field is also intended to be used to differentiate between material with/without certain properties, like adhesive backing, or UV resistance.
- [ ] Add html markup support for specifying text color, equivalent to using the `text_color` field. We'll use `<tc:color>` to specify the text color, where `color` can be a named color (e.g., "red", "blue") or an abbreviated 1-char code supported by the `TextColor` class. For example, `<tc:red>This text is red</tc>` or `<tc:r>This text is red</tc>`.
