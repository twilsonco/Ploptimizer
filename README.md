# Ploptimizer

Plot optimizer (Ploptimizer) is a deterministic, cross-platform Python tool for optimizing geometric toolpaths from HPGL/PLT plotter files generated by Cadlink EngraveLab Expert v10.

Ploptimizer minimizes tool-up travel time, and removes redundant (overlapping) strokes.

## Features

- **HPGL/PLT Parser**: Robust tokenization of EngraveLab-generated plotter files
- **Identity Validation**: Rigorous round-trip testing ensuring semantic equivalence
- **Diagnostic Visualization**: Color-coded path visualization showing cumulative distance traveled
- **Dual Logging**:
  - Text logging (`logs/optimizer.log`) with DEBUG/INFO/WARNING/ERROR/CRITICAL levels
  - CSV metrics tracking (`logs/job_metrics.csv`) for optimization analysis
- **Cross-Platform**: Uses `pathlib.Path` throughout; Windows-compatible output
- **Hot-Watch Daemon**: Automated directory monitoring for batch processing new/modified PLT files
- **Intra-Chunk Optimization**: Within-block path ordering and direction optimization while preserving fixed entrance/exit points
- **Label Generation Pipeline**: Create production-ready, per-cutter PLT files (plus PDF previews) from YAML job specifications — cascading typography, cutter compensation, drill holes, and bounds-aware bin packing across plates
- **Subcommand CLI**: `plt-optimizer optimize | generate | watch` for single-file optimization, spec-driven generation, and the headless hot-watch daemon

### Optimization Strategies

PLT-Optimizer provides multiple routing algorithms for MacroBlock traversal:

| Strategy | Description |
|----------|-------------|
| Nearest Neighbor + 2-Opt | (a.k.a. fast mode) Greedy nearest neighbor with 2-opt local search refinement |
| Insertion Heuristic | Cheapest Insertion Heuristic for TSP (greedy constructive) |
| Christofides-Serdyukov | S-T Path TSP with 5/3 approximation guarantee |
| Simulated Annealing | Probabilistic technique for approximating the global optimum of a given function |
| Genetic Algorithm | Population-based evolutionary search over block orderings |
| ParallelEnsembleStrategy | Runs multiple strategies in parallel, selects best result |

For **fast mode** (single strategy), use `--fast-mode` flag.

The **ParallelEnsemble** strategy runs each member strategy in its own worker
process with a configurable per-job timeout (default 10 seconds). Any strategy
that exceeds the timeout is aborted and marked as failed; if every job fails,
the serial Nearest Neighbor + 2-Opt fallback runs instead. Tune it with
`--ensemble-timeout <seconds>` (watch daemon and benchmark) or the
**Ensemble Timeout (s)** field in the settings window.

In the **batch benchmark tool**, the same `--ensemble-timeout` budget bounds
*every* optimization job: each individual strategy run executes in its own
killable subprocess and is marked `failed` (with `timed out after Xs`) when it
exceeds the budget, so one pathological file/strategy pair can no longer stall
the whole batch.

## Command-Line Interface

The `plt-optimizer` executable (or `uv run plt-optimizer` from source) exposes three subcommands:

### `optimize` — single-file toolpath optimization

```bash
plt-optimizer optimize input.plt                    # -> input_optimized.plt
plt-optimizer optimize input.plt -o output.plt --fast-mode
```

Parses, profiles (text vs. structural), optimizes, and writes one PLT file. Defaults to the ParallelEnsemble strategy (runs multiple strategies, keeps the best) unless `--fast-mode` is given. Logs go to `./logs_optimize/` by default (`--log-dir` to change).

### `generate` — YAML specification to per-cutter PLT files

```bash
plt-optimizer generate spec.yaml                    # outputs beside the spec
plt-optimizer generate spec.yaml -o out/ --no-plots
```

Runs the three-phase generation pipeline (label resolution with cutter compensation → bounds-aware bin packing → per-label rendering/assembly) and writes:

```
out/plt/30_txt_<job_id>.plt          # one file per text cutter
out/plt/15_bh_<job_id>.plt           # borders + drill holes together
out/pdf/30_txt_<job_id>.pdf          # simple-outline previews (--no-plots skips)
out/pdf/01_all_<job_id>.pdf          # combined preview per plate
```

File names read `[<material>_][<plate>_]<cutter>[_<color>]_<kind>_<job_id>`:
the sanitized material tag (e.g. `wk(uv)` -> `wk_uv`) leads, so all sheets of
one stock sort together, and it appears only when the job declares a
`material`; the 2-digit plate number follows it and appears only when a
material spans more than one plate (its presence signals that material needs
multiple sheets); the cutter is the diameter in integer thousandths of an inch
(`0.030` -> `30`). Every name carries only ASCII letters, digits and
underscores: international characters are transliterated (`Café` -> `Cafe`) and
punctuation collapses to a single underscore (underscores excepted). PLT names
are capped at 39 characters including the extension -
the plotter controller rejects longer names, so a long job name is shortened
from the right.

A cutter engraves **wider** than its nominal diameter: a V-bit with roughly
45-degree flanks cuts a groove whose width grows with the cut depth. The
`cutter_buffer_text` and `cutter_buffer_routing` fields (job-spec cascade
job → plate → label → line, with `job-config.json` shop defaults) add that
kerf in inches to the text cutters and to the boundary/drill-hole cutter, and
the pipeline uses the resulting *effective* width everywhere material removal
matters — kerning clearance, text/hole collision gaps, drill-hole cutter
compensation, packing kerf and the PDF preview stroke widths — while the
toolpath height compensates so engraved text stays exactly `text_height` tall.
The **tool** stays physical: pen splits and the `<cutter>_txt_` / `<cutter>_bh_`
file names keep naming the nominal diameter, so `30_txt_*.plt` is still the
0.030in cutter. Set both buffers to `0.0` to engrave and proof at the nominal
diameters.

Cutter sizes come from `tools.json` (`--tools` to point elsewhere) and job-spec defaults from `job-config.json` (`--job-config` to point elsewhere). Keep one `tools.json` + `job-config.json` pair per engraver/toolset and swap them with the two flags. The config supplies the top-most (job/plate) layer defaults — e.g. `max_h_compress`, `hole_margin`, `min_hole_margin`, `hole_text_collision_distance`, `cutter_buffer_text`, `cutter_buffer_routing`, `plate_width`/`plate_height`, `left_clearance`/`top_clearance` — and any of these configured nowhere becomes a required job-spec field. The `plates:` section is optional: a spec that omits it packs onto default sheets sized by the config's `plate_width`/`plate_height`, overflowing onto as many sheets as needed. Text–hole collisions are treated as unacceptable output: the job aborts with a non-zero exit code so the spec can be revised. Every config field is documented in [`JOB_CONFIG.md`](docs/skills/engraving-jobs/engraving-job-complete-reference/references/JOB_CONFIG.md) (auto-generated from the model; the file's `$schema` key also enables per-key hover docs in a JSON-aware editor), and every job-spec field in [`JOB_SPEC.md`](docs/skills/engraving-jobs/engraving-job-complete-reference/references/JOB_SPEC.md). See [`docs/INTEGRATION_TESTING.md`](docs/INTEGRATION_TESTING.md) for the full pipeline walkthrough and [`plt_optimizer/generate/AGENTS.md`](plt_optimizer/generate/AGENTS.md) for the YAML job-spec schema. Example specs live in [`examples/`](examples/).

### `generate --jobset` — batch several job specs onto shared plates

```bash
plt-optimizer generate --jobset batch.yaml              # no positional spec
plt-optimizer generate --jobset batch.yaml -o out/ --no-plots
```

Jobs arrive in batches, and packing each job on its own wastes the gaps between
them. A `jobset:` file lists complete job specs; one `generate` run resolves
every member and then packs the whole set onto **one pool of plates**, so a
label of job B can fill the corner job A left free:

```yaml
# batch.yaml - paths are relative to this file; order is the layout order
jobset:
  - job: "jobset example A.yaml"
  - job: "jobset example B.yaml"
```

Each member keeps its own cascade, fonts, cutter compensation, holes and
label geometry: the front half of the pipeline runs per job, and only packing
and emission are shared. On a shared plate emission is **per tool** - one
borders-and-holes file for every job using that cutter, one text file per cutter
and colour - so a cutter never walks the sheet once per job. Jobs sharing a tool
are routed together; a layer splits per job only when the tool's parameters
(`tool_options`) disagree, and the run then warns that the cutter engraves twice
per sheet. A batch writes the files a standalone run writes for the layers a job
owns alone, and names the shared layers for the batch. Strokes are never routed
across two layers and a layer never mixes two tools, so the work is engraved
layer by layer, sheet by sheet, in file order.
A shipped batch example lives in
[`examples/job_specs/job_sets/jobset example.yaml`](examples/job_specs/job_sets/):
two jobs (one declaring a 24x16 sheet, the other a 12x4), packed by the same
`columns` fill order - all of the set's work lands on the 24x16 sheet and the
second member's unused sheet stays unpacked.

For a set named `Evening Batch` whose members resolve to job keys `Job_A` and
`Job_B`, the output tree is:

```text
out/plt/kw_15_bh_Evening_Batch.plt       # every job's borders + holes: one tool, one run
out/plt/kw_45_txt_Job_A.plt              # a layer one job owns alone keeps its own name
out/plt/kw_60_txt_Job_B.plt              # job B's own cutter/colour
out/pdf/all_Evening_Batch.pdf            # the plate proof - every label outlined by job
out/generation_report/report.json        # the batch report
out/generation_report/summary.txt
out/generation_report/jobset.json        # the manifest: jobs, plates, files, gate findings
out/Job_A/generation_report/report.json  # one report per job, same shape as --spec
out/Job_B/generation_report/report.json
```

The PLT names follow the single-job contract
(`[<material>_][<plate>_]<cutter>[_<color>]_<kind>_<job_id>`). The last token is
the **owning job** for a layer that carries one job's strokes - so those files
are exactly what that job writes standalone - and the **batch** for a layer the
jobs share, whose membership the reports record. The difference from separate
runs is that the work lands on shared sheets, engraved one tool per pass.

Every report carries its own `usage` accounting, so a job inside a batch bills
exactly as it would have run alone. The batch report adds a `jobset` block (the
set identity, each member's `distance_total` / `time_total` / report path, and
the `cross_job` measure of what sharing saved) plus `by_job` breakdowns inside
`usage.distance` and `usage.time` (per-job cutting / rapid / plunge / z-up /
dwell seconds and the job's `share` of the run). The `jobset.json` manifest is
the shop's audit trail: `plates[]` names the jobs and the label ids of each
job on every sheet, and `files[]` maps each written file to its plate, layer
(`text` / `borders_holes`), cutter, colour, owning jobs, byte size and sha256 -
so dropping one job's layer on a re-run is a lookup, not a guess.

The plate proof is the visual key: **every label carries a dashed outline in its
job's colour, drawn inside its own border** (a fixed palette, colour first then
line style, indexed by the job's position in the file), one box per label so a
label's owner is read off directly, with a legend collapsing to one row per job.
The box sits 0.05in inboard of the label's slot on every side, so the key reads
as part of the label instead of adding a second outline in the scrap margin
between two labels that abut. The treatment is the same on a sheet one job
occupies alone - an outlined label is identified at a glance, where "no box
here" would force you to infer ownership from the absence of a key. A normal
single-job `generate` run draws no overlay at all (it has one
job, so there is nothing to key), and a one-job sheet inside a batch gets no
second proof file, because that whole-sheet proof already is that job's proof.

Before the batch packs, a gate checks that the members can be packed together.
It **fails** the run (listing every problem at once) when members declare
different `layout` fill orders - one shared sheet has one fill order, so
`columns` cannot mix with `rows`, and a `*-simple` grid fill cannot share a
pool with the rectangle packer - when a member declares one plate id twice,
when the set lists no job, and when a member file is missing, listed twice,
is itself a jobset (jobsets do not nest), or fails to parse. It **warns** (the
run continues) when pool-wide settings disagree - `allow_rotation` and the
job-level plate clearance take the first member in file order - and names the
sheet geometries several members declare (those sheets pool, and the warning
lists the owners). A `plate_id` pin the pool cannot honour is named and
dropped, so the label packs in the pool instead of silently reserving a sheet.
Pre-flight a batch with `python scripts/validate_job_spec.py batch.yaml`, which
accepts both spec kinds (exit 0 on warnings, 1 on a gate error).

### `watch` — hot-folder daemon

```bash
plt-optimizer watch --watch-dir /path/to/watch --output-dir ./optimized
```

Watches a directory for new/modified `.plt`/`.hpgl` files and optimizes each after it has been quiet for `--debounce-seconds` (default 2.0). Optimized files are written atomically (staged under `<output-dir>/.incomplete/`); originals are moved to `--processed-dir` if given, otherwise deleted. Files that fail optimization are copied to the output directory as `<name>_unprocessed.plt` for manual review. Options: `--fast-mode`, `--debug-save-files`, `--log-dir`. Running the tray application (Windows) uses the same engine in the background.

## Batch Benchmark Tool

A standalone utility lives in `plt_optimizer/cli/benchmark.py` for processing every `*.plt`
file in a directory and comparing the effectiveness of each strategy across the
batch. It is intended for diagnosing files that fail in production and for
benchmarking the optimization strategies on real-world inputs.

### Usage

```bash
python plt_optimizer/cli/benchmark.py /path/to/cad_files/
python plt_optimizer/cli/benchmark.py /path/to/cad_files/ --same-row-preference 1.5
python plt_optimizer/cli/benchmark.py /path/to/cad_files/ --ensemble-timeout 30
python plt_optimizer/cli/benchmark.py /path/to/cad_files/ --log-level info
```

Log verbosity (the text log and `logs/optimizer.log`, including every spawned
worker process) defaults to `WARNING` and is controlled with `--log-level
{debug,info,warning,error,critical}`.

The winners post-processing described below also runs automatically at the end of
every benchmark. To re-run it standalone against an existing `report.csv` (without
re-processing any PLT files):

```bash
python plt_optimizer/cli/benchmark.py --analyze-only /path/to/cad_files_benchmark/report.csv
```

### Output

A `<input_dir_name>_benchmark/` directory is created adjacent to the input
directory, containing:

```
<input_dir_name>_benchmark/
├── report.csv                              # Per-file + per-strategy summary
├── ensemble_report.csv                     # Summary of ensemble strategy results
├── report_rapid_improvement_winners.csv    # Per-file best rapid improvement
├── report_time_winners.csv                 # Per-file fastest strategy
├── report_combined_winners.csv             # Per-file best quality/speed balance
├── report_winner_summary.csv               # Per-strategy win counts + runtime stats (mirrors stdout table)
├── optimized/
│   ├── nn2opt/                             # Optimized PLT files per strategy
│   ├── insertion/
│   ├── christofides/
│   ├── sa/
│   └── genetic/
└── plots/                                  # Before + after plots per file/strategy
```

- `report.csv` contains one row for each file, for each strategy (number of files ⨉ number of strategies total rows). Each row includes the job's own runtime efficiency columns `ms_per_path` and `ms_per_segment` (the row's `time_ms` divided by its `before_paths` / `before_segments`); these are blank for failed rows or reports predating the `before_paths`/`before_segments` columns.
- `ensemble_report.csv` contains one row for each file, summarizing the results of the ensemble strategy, which selects the best result from multiple strategies.
- The three `report_*_winners.csv` files are generated by an automatic post-run analysis that re-reads `report.csv`. For every file with at least one successful strategy (excluding the `no-opt` baseline), the winning strategy row is recorded under three criteria:
  - **rapid improvement winners** — highest `rapid_improvement_pct`
  - **time winners** — lowest `time_ms`
  - **combined winners** — highest blend of both: each criterion is min-max normalised to [0, 1] within the file, then averaged with equal weight (the extra `combined_score` column holds the score). Ties resolve to the faster strategy.
- The winners CSVs inherit the full `report.csv` schema, so each winning row carries its own `ms_per_path` / `ms_per_segment` runtime columns (recomputed on the fly when analyzing historical reports written before those columns existed).
- A win-count + runtime-statistics summary table (strategy × criterion) is printed to stdout at the end of the run, and the same table is written to `report_winner_summary.csv` (one row per strategy: `strategy`, `rapid_improvement_wins`, `runtime_wins`, `combined_wins`, plus batch-wide per-strategy runtime stats — `max_time_ms` (slowest single-file run) and min/max/average runtime per path (`min_ms_per_path`, `max_ms_per_path`, `avg_ms_per_path`) and per segment (`min_ms_per_segment`, `max_ms_per_segment`, `avg_ms_per_segment`); unavailable ratios appear as `n/a`).

## Installation

> **Note:** This program is primarily intended for **Windows** users. A pre-built installer is available from the [Releases page](https://github.com/twilsonco/PLT-Optimizer/releases) for the simplest setup.

### Windows (End Users)

> **Requires Windows 10 or later.** The pre-built `Ploptimizer` installer (system tray
> GUI) is not supported on Windows 7. On Windows 7, run the headless CLI watch
> daemon instead — see [macOS / Linux / Windows 7](#macos--linux--windows-7)
> below and the setup guide in
> [`README_DEV.md`](docs/README_DEV.md#windows-7-notes).

1. Download `Ploptimizer-Setup-<version>-windows-x64.exe` from the [latest release](https://github.com/twilsonco/PLT-Optimizer/releases/latest).
2. Run the installer. The default is a per-user install to `%LOCALAPPDATA%\Programs\Ploptimizer\` (no admin needed); the wizard also allows a machine-wide install to `C:\Program Files\Ploptimizer\` if you elevate.

   > **Note:** The installer is unsigned, so Windows SmartScreen may show an "unknown publisher" warning on first run — click **More info** → **Run anyway**.

3. Launch **Ploptimizer** from the Start menu (or the desktop shortcut, if you opted in during setup). The settings window will open automatically on first run.
4. Configure the program to your liking. You may want to change:
   - **Watch directory** — where new PLT files appear (e.g., your Cadlink export folder)
   - **Output directory** — where optimized PLT files are saved
   - **Log directory** — where text logs and CSV metrics are written
   - **Processed directory** — where source files are moved after optimization
5. Right-click the Ploptimizer icon in the system tray to access settings or quit the program.

Once configured, the program runs silently in the background and will automatically optimize any new or modified PLT files placed in your watch directory.

### macOS / Linux / Windows 7

If you are on macOS or Linux, or Windows 7, or you prefer to build the executable from source, see [`README_DEV.md`](docs/README_DEV.md) for full installation instructions, including prerequisites, building with PyInstaller, and running the headless watch daemon.

> **Note:** The system tray GUI is Windows-only. On macOS and Linux, only the headless CLI watch daemon is available.

> **Windows 7 is CLI-only.** The system tray GUI and the pre-built
> `Ploptimizer.exe` installer are **not** supported on Windows 7 (the executable
> is built with a toolchain that requires Windows 10+, and the tray GUI needs
> dependencies unavailable on the Python 3.8 runtime Win7 requires). The only
> supported way to run PLT-Optimizer on Windows 7 is the **headless CLI watch
> daemon** (`plt-optimizer watch --watch-dir ...`), which runs on Python 3.8
> without matplotlib. [`README_DEV.md`](docs/README_DEV.md#windows-7-notes)
> walks through the Python 3.8 setup and running the watch daemon as a
> **Task Scheduler** task so it starts automatically at boot.
