# TODO List

- [ ] Multi-stroke font support
  - For font extraction from PLT files, the naming convention for font plt files will change to `<font name>_<text height inches>_<reference character>_S<number of strokes>.plt`. The number of strokes is then stored in the `plt_fonts.json` file. This part only involves changes to `extract_plt_fonts.py`. We'll overwrite the fonts json file completely, as we currently do, each time the extraction script is run. If a number of strokes is omitted from the font plt file name, it will be assumed to be a single-stroke font.
  - The main changes will be on the rendering side of things. The font name alone is sufficient for specifying any single/multi-stroke font, so there's no need to change the naming convention for specifying fonts in yaml job specs. 
  - The number of strokes will be looked up from the `plt_fonts.json` file during rendering.
  - We'll create a new float field, cascading job -> plate -> label -> line, and in job-config.json, defaulting to 0.25, bounded to [0.1, 0.5], that will control the amount of desired stroke overlap for multi-stroke fonts. Example: An overlap_ratio of 0.25 means a stepover distance of $75\%$ of the cutter width ($1 - \text{overlap\_ratio}$).
  - Implement an algorithm to calculate the recommended cutter tip width ($W_{\text{cutter}}$) based on the target text height, stroke count, and overlap setting.
    - Single-Stroke Logic (Existing):$$W_{\text{cutter}} = \text{text\_height} \times 0.12$$
    - Multi-Stroke Logic:Multi-stroke fonts are engineered to produce an overall target stroke width ($W_{\text{total}}$) proportional to the text height. Base target stroke width scales with character proportion (typically $12\%$ to $16\%$ of text_height for bold multi-stroke glyphs).$$\text{Stepover Factor } (S_f) = 1 - \text{overlap\_ratio}$$$$\text{Effective Stroke Units } (U) = 1 + (N - 1) \times S_f$$$$W_{\text{cutter}} = \frac{W_{\text{total}}}{U}$$Where $N$ is stroke_count and $W_{\text{total}} = \text{text\_height} \times \text{target\_boldness\_factor}$ (default 0.14).
    - Standard Fallback Rules of Thumb (Relative to Text Height):If $W_{\text{total}}$ is not explicitly defined by font metadata, derive cutter tip width as a ratio of text_height:
      - 3-Stroke: $\approx 5.5\%$ of text height (with $25\%$ overlap)
      - 5-Stroke: $\approx 3.8\%$ of text height (with $25\%$ overlap)
      - 7-Stroke: $\approx 2.8\%$ of text height (with $25\%$ overlap)
  - With the cutter size in hand, we can use existing code for border/hole/text/descender collision avoidance.
  - All in all, this should be a fairly straightforward implementation.
- [ ] HTML syntax support in label text contents:
  - We'll add a new field for specifying the brackets used for html syntax `html_brackets` — cascading job -> plate -> label -> line, and in job-config.json, defaulting to `<>`. `html_brackets` is a two-character string, the first of which specifies the left bracket, and the second the right bracket. This way, if a label contains chevrons, we don't need to worry about it being incorrectly recognized as html syntax. There's no need to specify a similar new field to specify the slash character, because we only look for the slash when it's enclosed by the html brackets (and whatever command was used), and when that follows the opening html enclosure to define a region of html-modified text. That is, not every forward-slash is taken to be part of html syntax, only those that occur in e.g. `</i>`. 
  - [x] <i>Italicization</i>: performs transform of HPGL characters for PLT fonts (with appropriate adjustments to spacing/kerning), or uses native TTF italics (falling back to PLT transform if not available). Adds an optional `italic_angle` field to control the slant angle for PLT italics, cascades job -> plate -> label -> line, and in job-config.json, defaulting to 12 degrees.
    - More html markup types will be added, so this needs to be properly abstracted into a framework that can handle different types of text transformations.
  - Time to add another type of html markup for label text.
  - [ ] <b>Bold</b> text support: will result in emboldened text being a thicker cutter (the next size up in inventory) with adjusted spacing/kerning accordingly.
  - [x] <u>Underline</u> support: for PLT, we'll add an underline that goes the full width of a line (from the left of the first character's bbox to the right of the last character's bbox), *minimally* breaking the line to accomodate characters that descend below the baseline, based on the would-be collision between the underline and the character. For TTF, use font's underline if present, otherwise do the same as for PLT.
    - Shipped as per-run underlines (each maximal `<u>` run spans its own glyphs' ink, not the whole line) and always PLT-style geometry for both families (the font's own underline metrics are deliberately never consulted). New `underline_offset` field (cascades job -> plate -> label -> line, job-config.json, default 0.0): the centerline sits `cutter_diameter + underline_offset` below the baseline, so the engraved underline's top edge floats exactly `underline_offset` below the engraved baseline stroke; the same radius triggers the minimal gap cuts (true 2D ink distance, touching = safe).
  - [ ] Specify different font for different parts of a label text line. (e.g. using wingdings symbols in a text line). Syntax: `<f:font name>some text</f>`
    - [ ] Maybe support mixed PLT/TTF fonts?
  - [ ] <sup>superscript</sup>/<sub>subscript</sub>, or arbitrary floating-point adjustment of baseline (where 0 is the current baseline, 1 is the capline, and -1 is the the $capline - baseline$ distance *below the baseline*). Arbitrary adjustment will work via an optional argument to the `sup` and `sub`, e.g. `1<sup:0.3>st</sup>`. For superscript/subscript, we'll also downscale the character to achieve a proper look. A new float schema field, `supersubscript_downscale`, cascades job -> plate -> label -> line, and in job-config.json, default 0.5, will control the amount of downscaling (bound to [0.2, 1.0]); eg if 0.8, downscale to 80% off original size. *When sup and sub are used with their optional float argument, no scaling will be applied.*
  - [ ] Small caps, `<sc>some text</sc>` will apply the small caps transformation to just the `sc`'d text. If a small caps transformation is applied to text that is already in small caps, it will have no additional effect.
- [ ] Add a new optional field enum, `border_hole_options`, that lets the user control files produced for borders-holes: `separate` (produce separate files for borders and holes), `combined` (default, produce a single file combining borders and holes), `borders_only`, `holes_only`.
